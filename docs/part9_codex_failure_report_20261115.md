# รายงานสาเหตุที่ Codex ทำท่อน 9 ไม่สำเร็จตามเวลาที่ควร

วันที่: 2026-11-15  
โปรเจกต์: รักลำเอียง — ท่อน 9  
ผู้ใช้รายงานว่าเริ่มงานโดยมีลิมิตประมาณ 60% และขณะขอรายงานเหลือประมาณ 26% หลังใช้เวลาเกือบ 2 ชั่วโมง

## ข้อสรุปตรง ๆ

ปัญหาหลักไม่ใช่ว่าโมเดลคิดเนื้อเรื่องไม่ได้ แต่เป็นการดำเนินงานที่ไม่มีเส้นทางควบคุม iClone ที่มั่นคงตั้งแต่ต้น และ Codex ปล่อยให้เกิดการตรวจสถานะ/ลองเครื่องมือ/รอผลซ้ำหลายรอบก่อนสร้างชิ้นงานจริง การใช้โมเดลแรงจึงไม่ได้ช่วยเมื่อขั้นตอนลงมือถูกส่งไปยังช่องทางที่คุมโปรแกรมไม่ได้หรือคุมผิดหน้าต่าง

Codex ควรตรวจเส้นทางควบคุมจริงเพียงครั้งเดียว แล้วเลือก watcher + Python เป็นเส้นทางหลักทันที แต่กลับเสียเวลาไปกับ Dino, UI Automation, การสลับหน้าต่าง, การหาเมนู, การอ่านเอกสารซ้ำ และการรายงานว่า “กำลังตรวจ” หลายรอบ ทั้งที่ภาพใน iClone ยังไม่เปลี่ยน

## สิ่งที่เกิดขึ้นจริง

1. เริ่มต้นด้วยการอ่านสถานะและพยายามคุม iClone ผ่านหลายเส้นทาง ทั้ง Dino, PowerShell UI Automation, Agent Desktop และ Computer Use แทนที่จะล็อกเส้นทาง watcher ที่ใช้งานได้จริงตั้งแต่ต้น
2. โปรเจกต์ระบุว่า iClone อยู่จอ 2 แต่คำสั่งคีย์บอร์ดช่วงแรกไปผิดหน้าต่าง/ผิดจอ ผู้ใช้จึงเห็นภาพเดิมตลอด
3. Agent Desktop ใช้งานไม่ได้เพราะ `PERM_DENIED: private file DACL grants an untrusted principal`
4. iClone เปิด accessibility tree ได้น้อยมาก ทำให้ PowerShell UI Automation เห็นเพียงหน้าต่างหลัก แต่ไม่เห็นปุ่ม/เมนูที่ต้องใช้
5. Computer Use ไปถึงกล่อง `Apply Audio` และนำเข้าเสียงจน progress จบ แต่การตรวจแถว Sound และการบันทึกผ่าน UI ถูกขัดจังหวะด้วย `aborted by user` จึงต้องหยุดส่ง input ตามกฎของเครื่องมือ
6. สคริปต์ชื่อ Part 9 เดิมในโปรเจกต์ เช่น `scripts/ic8_part9_cams.py` และ `scripts/ic8_part9_move.py` เป็นงานคนละเรื่อง/คนละฉาก จึงนำมาใช้กับรักลำเอียงไม่ได้
7. การสร้างกล้องครั้งแรกอาศัยสมมติฐาน API ที่ไม่ตรงกับ iClone รุ่นที่เปิดอยู่: `RScene.CreateObject` ไม่มีใน runtime นี้
8. การโหลดกล้องจาก `Dolly Pan.iCam` สร้างวัตถุกล้องที่ไม่มี `Transform` control จึงใช้จัดเฟรมไม่ได้ ต้องเปลี่ยนไปใช้ `Long Shot01.iCam`
9. หลังสร้างกล้องและเรนเดอร์ภาพนิ่งแล้ว QA พบว่าภาพใช้ไม่ได้: หลายช็อตติดผนัง/มืด, close-up พ่อจับด้านหลังลำตัวผิดตำแหน่ง และช็อตวารีหลุดเป้าเห็นส่วนเท้า/พื้น จึงยังห้ามเรียกว่าเสร็จ
10. มีการใช้ subagent/การรอผลหลายช่วง ทำให้เกิด latency และการรายงานซ้ำ โดยไม่ได้เพิ่มความคืบหน้าใน iClone ตามสัดส่วน

## เหตุผลที่ใช้ลิมิตมาก

ตัวเลข 26% เป็นข้อมูลที่ผู้ใช้เห็นจากหน้าจอ Codex; โปรเจกต์นี้ไม่มี API สำหรับตรวจบัญชีการใช้ลิมิตโดยตรง จึงยืนยันวิธีคิดของระบบไม่ได้ แต่จากบันทึกงาน สาเหตุที่กินลิมิตโดยไม่เกิดผลงานตามสัดส่วนมีดังนี้

- อ่านเอกสารโปรเจกต์ขนาดใหญ่หลายไฟล์และมี output ถูกตัดเพราะยาวเกิน
- เรียก `inspect_scene` ซึ่งส่งรายการพร็อพ 137 รายการและไฟ 29 ดวงกลับมาทั้งชุด
- ลอง UI control หลายระบบที่ล้มเหลว แล้วเริ่มเส้นทางใหม่ซ้ำ
- รอ/ถามสถานะ subagent หลายรอบ
- สร้างและแก้สคริปต์ stage/camera หลายรอบจากข้อผิดพลาด runtime
- เรนเดอร์ still QA 8 ภาพแล้วพบว่าจัดเฟรมผิด ต้องแก้ใหม่
- ส่งข้อความสถานะจำนวนมากก่อนมีผลเปลี่ยนแปลงที่ยืนยันได้

ดังนั้น “โมเดลแรง” ไม่ได้แปลว่างานจะเร็ว หากมันยังต้องลองเส้นทางควบคุมที่เสีย, รับ context ปริมาณมาก, และไม่มี stop condition ที่ตัดการวนซ้ำเร็วพอ
